# Codex 一括指示：my-search 技術記事コーパスと統計的評価の準備

現在の `my-search_public` リポジトリに対して、以下を順番に自律実行してください。
目的は**実際の日本語技術記事を十分な数だけ集め、妥当なクエリ・正解IDと共に、独立した検索品質検証ができる状態にする**こと。記事500件を統計的に十分な標本数だと誤認しないこと。

## 1. コーパス取得

- 本フォルダの `scripts/collect_articles.py` を使用。最小2,000記事、目標2,500記事。条件を満たすまで、許される公式フィード・公式APIによるソースを追加する。少数の著者や技術カテゴリへ極度に偏らせない。
- Zennの公式RSS、Qiita公式APIの利用規約・レート制限を守る。**QiitaのHTMLスクレイピングは禁止**。記事本文の複製・再配布は自動許可されない。既定ではタイトル・URL・タグ・フィードの短い説明だけを保存し、本文取得が必要なら許諾と利用条件を個別に確認し、ローカル限定で処理する。
- 各レコードの取得方法、公開URL、取得日、全文の有無を記録。URLによる厳密重複排除に加え、同一記事の転載・極端な類似も検査する。収集数の不足を水増しで補わない。
- `local_article_corpus/` 以下の元データをGitで追跡しない（`.gitignore` を追加）。既存DB、ユーザーカード、メモは一切変更しない。
- 収集処理が対象実行環境でアクセス不能なら、エラー・実取得数を報告。成功扱いしない。

## 2. 開発用検索テストの準備

- `scripts/design_and_judge.py plan` で対象文書IDの固定ハッシュによる400/400/1,200の抽出を行う。クエリの内容・検索順位を見て分割しない。
- `scripts/make_dev_queries.py` による自己派生クエリを**開発用の暫定回帰テスト**として利用してよい。これを自然検索クエリ、最終ホールドアウト、実利用の代表標本と呼ばない。
- 公開の自然検索クエリと正解記事IDとの対応が得られる場合のみ、明示的な出典と確認済み正解を採用する。検索結果を見て正解を調整しない。
- 既存 `quality/e2e/` の検索API・BM25ベンチマーク手順を優先して再利用し、実際のUIの検索経路を実行する。
- 開発用・検証用で原因分解→改善→回帰テストを繰り返す。重要語の欠落、候補生成、ランキング、レイテンシを分離測定。公開コーパスがタイトル・短い説明だけの場合、**その条件の品質**として明記し、全文検索性能と称しない。

## 3. 統計的な最終評価

- 本パッケージの `scripts/design_and_judge.py sample-sizes` の計画を基準に、独立代表検索試行1,200件を目標にする。片側α=.025、H0:p<=.95、Hit@10が成功の唯一の主指標。95%超のClopper–Pearson片側下限を要件とする（1,200件では少なくとも1,155件成功）。
- 集計前に検索方式、Top10、タイムアウト、欠損、対象コーパス、対象クエリ、評価ビルド指紋、標本分布を固定する。評価を結果に合わせて繰り返さない。
- ラベル付きの自然検索クエリが足りない場合、無理に認定しない。クエリ著者、正解対象、言語・難度の相関がある場合はクラスタを保持して推定し、独立二項モデルだけを使わない。
- ユーザーによる自然な保存記事再発見率までの一般化を主張しない。公開記事コーパス・自然検索クエリ源の分布に限定した結論を出す。
- 元のBooks・Moviesは開発診断に利用できるが、使用済みholdoutを「新規」扱いしてはならない。

## 4. 検証と報告

- 収集した実記事数、同一タイトル/URL/著者偏り、ソース別・カテゴリ別の内訳、本文利用可否、APIエラーと出典を提出。
- 開発用テストのベースライン、変更履歴、回帰、既存本番検索との比較、p50/p95とメモリを提出。
- 未使用の独立自然クエリと正解ラベルが1,200件用意できたか判定し、ない場合 `NOT_EVALUABLE` と報告。自然検索記録を人工生成して埋めない。
- `npm run typecheck`、関連Vitest、実APIを使うテストを実行し、未実行は未実行と報告。
- **ユーザーの既存データを守り、commit/pushしない。**
