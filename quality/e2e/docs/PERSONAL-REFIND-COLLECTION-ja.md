# 本人の再発見質問を段階的に集める

目標: [検索目標](../../../docs/search-goals-ja.md)。この手順は収集方法の定義であり、収集済み・同意済みの宣言ではない。

## 保管と準備

記入済みテンプレート、本文、検索文、正解ID、DBコピー、結果はすべて `quality/e2e/local/personal-refind/` 配下に保管する。この親ディレクトリは既存の `.gitignore` で除外済み。Git管理するのは空テンプレートと架空例だけとし、実データをチャット・外部サービスへ送らない。既存の `data/search-evaluation/` にはGit除外の例外があるため、新しい実データの保管先には使わない。

実測時はSQLiteのオンラインバックアップ機能、またはアプリ停止後の整合したバックアップで隔離コピーを作る。稼働中のDB本体だけをコピーしてWALの内容を落とさない。コピーのintegrity_check、記事ID・件数、メモ・本文の一致を確認し、評価プロセスのDB_PATHが隔離先であることを確認する。原本への移行・索引作成・更新はしない。

## 収集順序

1. 開発用20問を本人の記憶から作る。対象記事のタイトル・本文・検索結果を先に見ず、最初の検索文と記録時刻を確定する。開発用は意図的な想起課題でもよいが、作成経緯を記録する。
2. 検索後、本人が本当に探していた保存記事のIDと内容を確認する。記事が検索前から保存されていたこと、メモとの関連も確認する。不明なら `unresolved` のまま残す。
3. 最終評価用は実際に探す必要が生じた日常利用から集める。初回文を後から言い換えず、修正文や再検索は別の補助記録にする。検索前に正解タイトルを提示して質問を誘導しない。
4. 最終評価は開発用とは別の対象記事に限定する。同じ記事、または複数正解を介してつながる記事群を一つのグループとし、すべて同じ分割に入れる。重複が判明した場合は最終評価に使わず開発用へ移し、理由を残す。
5. 主評価、正確なタイトル検索、該当記事なし、正解未確認を記録する。主評価は自然な本人入力・曖昧な記憶・保存済み正解の本人確認を満たすもの。結果の良し悪しを理由に除外しない。
6. 最終評価は最初の適格100問を既定とする。100問を超える件数を使う場合は収集開始前に件数を固定する。未確認・不適格件数と理由も台帳に残す。途中の成功率を見て停止・延長しない。

最終評価用の質問や結果を方式調整に使用したら、そのセットを開発用へ変更する。既に閲覧・調整したセットを新規holdoutと呼ばない。本人の同一ユーザー内の結果であり、他ユーザーへの一般化はしない。

## 記録方法

アプリ内の任意参加欄を使う場合、まず `npm run personal-refind:init` を一度実行する。これは計画300件の個人コホートをGit除外領域に準備するだけで、検索文を記録しない。カード一覧と「探す」画面にある参加チェックは初期OFFで、同じローカル同意状態を共有する。同意を確認した後に限り、検索開始時に質問文・時刻・記事ID集合を固定し、APIから返った初回Top10・候補集合（取得可能な場合）・失敗・応答時間をローカルに追記する。カード一覧では検索入力後の順位付き応答を記録し、失敗時も検索後の本人確認欄を表示する。検索後に本人が検索目的を選び、正解記事を確認する。複数正解も選べる。旧調査の同意状態は引き継がない。

収集を始める前に、実際に使うアプリの `GET /api/refind-study/status` が `available=true`、`preregistered=true`、`buildMatches=true` を返し、計画件数と対象がこのコホートの内容に一致することを確認する。`buildId` も記録し、凍結時の実装指紋と照合する。いずれかが不一致・未登録なら検索を収集に使わず、アプリを正しいソースと収集ディレクトリで起動し直してから状態を再確認する。画面に収集欄が見えてもAPI状態が条件を満たさない場合、記録は開始しない。

収集は最大300検索で固定し、途中の検索成績を表示しない。主評価には内容の記憶・関連語による自然な再発見で、本人が正解確認し、検索前に保存済みで、開発用と質問・対象が重複しない記録だけを使う。収集終了後は `npm run personal-refind:export` が時刻順で最初の適格100件だけを `final/` に書き、超過分は選定外として別に保管する。タイトル検索・未確認・対象重複・質問重複は主評価へ混入させず別の確認先へ分ける。API失敗・タイムアウトも正解が本人確認できた自然検索なら適格記録として残し、成功率の分母から落とさない。

手動で記録する場合は、[空テンプレート](../templates/personal-refind-records.json)をローカル保管先へコピーする。`caseTemplate` は書式例で、`cases` には含めない。アプリ内収集を使う場合は、上の手順が評価ケースを生成するため、このテンプレートをコピーする必要はない。

評価CLIは1ファイルにつき1ケースのJSONオブジェクトを読む。隔離先に `development/` と `final/` を作り、前者へ `personal-dev-<id>.json`、後者へ `personal-final-<id>.json` として個別保存する。配列テンプレート全体をケースファイルとして置かず、`caseTemplate` の項目を埋めた1件のオブジェクトを保存する。`collectionChannel` には本人が自然な検索を行った状況を短く記し、質問文・タイトル・本文をGit管理対象へ書かない。

- `query` / `queryLockedAt`: 最初に確定した文と日時。訂正する場合は元記録を保持し、新規IDで理由を記録。
- `origin`: `human-memory-development` または `human-natural-refind`。AI作成は主評価に使わない。
- `category`: `memory` / `exact-title` / `no-saved-target`。未判定はnull。
- `split`: `development` / `final`。`targetGroupId` は正解集合の連結成分で固定。
- `goldIds` / `humanVerified` / `savedBeforeQuery` / `verifiedAt`: 本人の確認。未確認をfalse/nullから自動昇格させない。
- `eligibility`: `pending` / `eligible` / `ineligible` と理由。主評価への適格性はランキングを基準にしない。
- `observedSession`: 日常の初回結果。`evaluationRun` は後日の固定方式リプレイ。両者を混同しない。

方式・設定を事前に固定し、正解確認と分割の監査が通った後、マニフェストを一度作る。マニフェスト作成後に質問・正解・コーパス・実装・設定を変えた場合は最終セットから外し、開発用へ移す。凍結リプレイは新しい隔離ディレクトリに行い、例として `npx tsx scripts/bench/replay_frozen_personal_refind.mjs <private-freeze-manifest.json> <new-private-run-directory>` を使う。コマンドは検索文を出力せず、観測・結果・SQLiteコピーをGit除外先に保存する。

将来の方式選択は凍結したセットの隔離リプレイで比較できるが、自然な初回セッションそのものの成功率とは別に報告する。実利用の測定かリプレイかは結果に必ず明記する。

## 本人に依存する未完了工程

開発用20問の作成、アプリのローカル収集への明示同意、日常利用からの最終100問以上の収集、正解・保存時点・適格性の確認が必要。収集UIやエクスポーターは質問を生成せず、AIは本人の記憶、自然な検索、正解判断を代行しない。
