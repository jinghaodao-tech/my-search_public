# 個人向け再発見評価プロトコル v1

2026-10-25。[検索目標](../../../docs/search-goals-ja.md)に対応する個別評価プロトコル。一般的な検索能力の主評価は[外部ベンチマークと本人データの評価範囲](EXTERNAL-AND-PERSONAL-EVALUATION-SCOPES-ja.md)で行い、このプロトコルの本人質問100問は一般性能目標の前提条件ではない。本人の保存庫での個別評価を主張する場合にのみ適用する。

`scripts/bench/personal_refind_metrics.mjs` は境界順位、API失敗、正解未確認、対象記事の連結成分、分割汚染、100問以上の件数、group bootstrapを集計する。`scripts/bench/freeze_personal_refind.mjs` は隔離先の最終記録・開発記録・SQLite・設定を検査し、質問本文を含めずに対象と指紋のマニフェストを作る。コーパス指紋にはカード本文・メタデータ・トークンキャッシュ・タグ/リンク関係を含め、別途3つのFTS索引内容もハッシュする。正解IDと作成時刻から、全正解記事が検索文固定時刻より前に保存されたことを照合する。`scripts/bench/audit_personal_refind_freeze.mjs` は現在の入力から指紋を再計算し、凍結後の変更を検出する。`scripts/bench/replay_frozen_personal_refind.mjs` は有効なマニフェストだけを受け入れ、新しいSQLite隔離コピーで固定質問を逐次実行し、実際の方式・フォールバック・再ランキング前候補ID・上位10件・API時間をローカル記録する。候補IDの応答はテスト環境で評価用フラグを明示した場合だけ返す。どれも記録は `quality/e2e/local/personal-refind/` 配下に限定し、ソースコーパスは読み取り専用で開く。モデルを使う場合はリポジトリ内のローカル成果物とSHA-256を必須とし、有料API依存を拒否する。

凍結は、本人の開発用20問以上と、対象記事グループが開発用と重ならない自然な最終質問100問以上を必須とする。開発記録も件数・検索文・記事グループをマニフェストへハッシュ化し、後から追加・差替えされたら監査を失敗させる。すでに方式比較に使った保存記事検索50問（`real-queries.json` 20問と `real-queries-v2.json` 30問）は、検索文をNFKC正規化・空白圧縮・小文字化してSHA-256化し、新規最終セットとの一致を拒否する。凍結マニフェストには50件の件数と集合ハッシュのみを記録し、質問文は書き出さない。これらの元データが欠落・変更されても凍結を拒否する。設定JSONは `method`、`settings` を必須とし、`settings.e5CandidateCount` は20〜500の整数で固定できる（省略時100）。ローカルモデル使用時は `model.id`、リポジトリ相対 `model.artifactPath`、実ファイルと一致する `model.sha256` を含める。例: `node scripts/bench/freeze_personal_refind.mjs <final-records-dir> <development-records-dir> <private-corpus.sqlite> <private-config.json> <new-private-manifest.json>`。監査は `node scripts/bench/audit_personal_refind_freeze.mjs <private-freeze-manifest.json>`、凍結後の品質測定は `npx tsx scripts/bench/replay_frozen_personal_refind.mjs <private-freeze-manifest.json> <new-private-run-directory>`。最終評価設定は `settings.modeId`（`/api/modes` のID）または正確な `settings.mode` とし、任意の `searchOptions` と `filters` も固定する。合成データによる凍結・改変検出・未確認・不足件数・分割混入・過去50問再利用拒否・監査連動採点のテストは `node --test tests/personal_refind_freeze.test.mjs tests/personal_refind_evaluator.test.mjs tests/personal_refind_freeze_io.test.mjs`。

SHA-256はローカル入力の変更検出用であり、第三者署名や改ざん耐性のある外部タイムスタンプではない。凍結後に質問・正解・コード・設定を変えたら監査は失敗し、そのデータは最終評価として使わず開発用へ戻す。マニフェストを作り直して同じ評価結果を認定し直してはならない。`summarizeQuality` の `freezeVerified` は互換用の純粋関数引数に残るため、最終判定では必ず上記監査の成功を確認する。

開発用の隔離API再生は `npx tsx scripts/bench/replay_personal_refind.mjs <source.db> <private-development-record.json> <new-private-output-directory>`。入力記録と出力先は `quality/e2e/local/` 配下に限定。原本をreadonlyでオンラインバックアップし、新しいコピーだけでAPIを実行する。自然文解析を含む1回の初回測定であり、1万件・3回の性能判定や最終評価には使わない。

## 凍結と品質判定

開発20問と最終100問以上を対象記事グループで分離する。最終評価の前にコーパス、質問・正解、適格性、件数、方式、モデル、設定、コード指紋、依存関係、評価手順の版を固定しSHA-256を記録する。未コミット変更を含むためGitコミットIDだけでは代替しない。モデル未導入や不足データを合格と扱わない。

`Hit@10 = 正解が上位10件に1件以上ある主評価質問数 / 全主評価質問数`。複数正解でも1質問につき成功は1。タイムアウト・APIエラー・空結果は分母に含め失敗とする。1質問の期限は自然文解析開始から30秒。フォールバックは実際に返った結果で計数するが、方式と発生件数を記録し、別方式の成績と偽らない。

正解未確認は収集台帳に残し、主評価に自動追加しない。凍結対象に未確認が残る、100問未満、分割汚染、正解がコーパスにない、記録欠落がある場合は `NOT_EVALUABLE`。不明例を黙って分母から落として達成としない。凍結済み主評価では不利な結果を除外しない。

十分な適格データと有効な凍結があり、実測Hit@10 >= 0.95なら `PASS`、それ未満は `FAIL`。95/100は点推定基準では合格。100問未満の100%は達成扱いしない。品質・性能・全体を別欄に記録し、未測定は `NOT_EVALUABLE` とする。

95%区間は対象記事グループを復元抽出するcluster bootstrap 10,000回、固定seed `0x25c0ffee`、質問数加重の成功率で算出する。グループは正解ID共有の連結成分とし、複数正解を介する依存もまとめる。乱数は32bit LCG `s=(1664525*s+1013904223) mod 2^32`、一様値 `s/2^32`。各反復で元のグループ数だけ抽出し、その全質問から成功率を計算。昇順10,000値の0始まり249番・9749番を区間端とする。

全成功・全失敗ではbootstrap区間が退化し得るため、その旨とグループ数を記載し、確実性の保証としない。区間下限95%は合格条件ではない。少数グループへの集中、同一人物・期間の偏りは限界として報告する。

候補coverageは、再ランキング直前の候補集合に正解が1件以上ある質問の割合。候補が記録できない場合は未測定とし、最終Top10から推定しない。失敗理由はAPI/timeout、候補欠落、候補内順位11位以下、原因未測定に分類する。

## 性能測定

現在のPCのCPU、RAM、OS、電源設定、Node/依存関係・モデル版、スレッド数、コーパスと索引指紋を記録。同一の1万件で単一利用者・逐次実行する。実記事が不足する場合は重複しない公開記事で補い、出典・件数・重複排除法を記録。品質用とは別の性能用コーパスであることを明示する。

開発用から固定した100リクエスト列を使う。20問の場合は同じ順を5周し、これは100個の独立質問ではないと記録。品質の最終セットを性能調整に消費しない。検索結果キャッシュはOFF。文書ベクトル・索引キャッシュは準備済みとして許可し、容量と準備状態を記録する。

最初にモデル未ロードの初回検索時間を別記する。モデルと索引を準備し、固定列を1回ウォームアップ後、同じ順で3回測る。各回の開始前に検索結果キャッシュOFFを確認。自然文解析API呼出しの直前から、検索APIの最終応答を受信するまでを単調時計で測り、解析・クエリ埋め込み・検索・再順位付け・ローカル通信を含める。初期索引作成とモデル取得時間は分離する。

各回p50/p95はnearest-rank（昇順n値のceil(p*n)番、1始まり）。3回それぞれp95 <=500ms、エラー・timeoutなしで性能PASS。エラー発生時は高速失敗で合格させずFAIL、時間も集計から落とさない。測定条件欠落・1万件未満・未測定はNOT_EVALUABLE。3万件は同手順で拡張性を報告するが合否は付けない。

各回のプロセスRSS/heapのピーク（100ms周期）、索引容量、初回検索時間を記録。測定後、隔離DB内の既知の1記事に架空の一意語を追加し、保存完了から検索反映までを100ms周期・上限30秒で測る。原文を復元し、メモ・本文・IDの保持を検証する。初期構築時間、モデル容量、更新反映時間に今回の数値合格閾値は置かない。

既定のFTS5形態素経路で更新反映と復元を再現する場合は、`npx tsx scripts/bench/measure_personal_search_update_reflection.mjs quality/e2e/local/personal-refind/scale-10000-v2/corpus.sqlite <unique-label>` を使う。測定ごとに新しい隔離コピーを作り、準備済みコーパスの指紋、個人カードの保持、更新後の検索反映、復元後の検索結果消失、SQLite integrity_checkを検証する。原本コーパスと `data/cards.db` は読み取り専用で開く。

## 比較と新規記事発見

現行アプリBM25、FTS5、ローカルベクトル候補検索、融合・再ランキングを同じ質問・コーパスで比較する。個人評価では開発分割で候補を選び、固定した1方式を本人の最終セットで判定する。最終結果から方式・重み・候補数を調整したらそのセットは開発扱いとなる。公開ベンチマークは一般性能の達成判定に使用できるが、本人の保存庫での個別達成を主張する根拠にはしない。

新規記事発見は別セットで本人が関連性0（無関係）/1（部分的）/2（有用）/3（非常に有用）を確認する。nDCG@10はgain=2^rel−1、discount=log2(rank+1)。候補方式のTop10をまとめたプールを方式名を隠して判定し、未判定は0にせず未完了。IDCG=0の問は別件数として報告し、再発見Hit@10には混ぜない。専用セットと基準値の確定は今回の範囲外。

## 既存機構との対応と不足

| 既存機構 | 再利用できる要素 | 今回との差・不足 |
|---|---|---|
| `docs/STUDY_PROTOCOL.md`（このディレクトリ） | 初回検索、本人確認、同意、ローカル記録の原則 | 旧版は複数人・二指標・信頼下限>95%の認定。今回の合否に適用しない。履歴保持 |
| `routes/refind_study_routes.ts`（リポジトリ直下） | 検索前のカード集合、イベントhash-chain、本人確認、build照合、複数 `goldIds` の記録 | 複数正解の記録は実装済み。評価分割・対象記事グループ・group区間・点推定判定を管理する完成品ではない |
| `internal_refind/tools/eval_refind.mjs` | ローカルAPIのTop10回帰確認 | 合成ケース。GET /api/cards経路で、エラーを品質分母から除く。今回の主評価器として使用不可 |
| `scripts/benchmark_tomt_saved_card_search.ts`（リポジトリ直下） | 隔離API比較、方式別記録 | 公開データ開発診断。現状の計時は自然文解析後から。今回の端から端までの性能目標には不足 |

このプロトコルの初版確定時点では、上記の既存実装や旧判定条件を変更しなかった。その後、本人の目標達成依頼を受けてローカル収集UI、今回の品質評価器、解析込み性能計時を実装・検証した。現在の実装・測定状況と残課題は[進捗記録](PERSONAL-REFIND-PROGRESS-ja.md)を参照する。空の記録テンプレートは手動記録用のままで、アプリAPIへの直接入力形式ではない。
