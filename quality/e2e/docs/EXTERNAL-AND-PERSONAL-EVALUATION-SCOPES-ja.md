# 外部ベンチマークと本人データの評価範囲

2026-10-26。`docs/search-goals-ja.md` の評価スコープ補足。

## 評価する主張を分ける

- **一般的な再発見能力**: 外部の人手由来 known-item retrieval を主評価にする。複数の公開コーパス・質問者に広げ、固定条件で再現可能な形で比較することで、一人の保存庫より一般化の根拠を得やすい。記事・Web文書に近い外部評価を優先し、書籍・映画・Wikipediaなど隣接領域の結果は別の転移指標として報告する。
- **保存記事への適用**: 外部ベンチマークは本人一人のデータより広い一般性能の評価に適するが、公開コーパスは通常、利用者が実際に保存した記事集合ではない。よって外部評価を主評価としつつ、対象文書の領域差を明記する。本人の隔離保存庫は、本人環境での転移確認として補助的に使う。複数利用者の実保存庫が得られる場合は追加の実利用検証として価値があるが、一般品質の主評価に必須とはしない。
- **新規記事発見**: 保存記事再発見と別セットで、人が候補記事の関連性を判定し、nDCG@10で評価する。

外部データを使うときも、出典・ライセンス・コーパス範囲・質問作成方法・ラベルの網羅性を明記する。既に探索・方式選択に使った分割は最終評価に流用しない。外部データ上の95%は、当該ベンチマークに対する達成であり、全ユーザーの実利用成功率95%を意味しない。複数利用者の保存記事評価では、質問と正解を各利用者の隔離コピーにひも付け、利用者IDを仮名化する。質問作成時に検索対象の記事タイトル・本文や検索結果を見せず、結果を見た後の候補提示で正解を確認する。利用者、正解記事グループ、利用者内の記事重複を考慮した分割・信頼区間を用い、利用者別の成功数も併記する。参加者数・募集条件・除外規則はデータ収集前に固定する。

## 一般性能と保存記事への転移を判定する手順

1. 公開外部ベンチマークを一般性能の主評価にする。候補ごとに言語、文書種別、質問作成方法、正解ラベルの適合度、利用条件、過去の使用歴を記録する。人手由来 known-item retrieval を優先し、記事・Web文書に近いコーパスを主に、FAQ・Wikipedia・書籍・映画等は別領域として報告する。
2. 外部評価から保存記事検索への転移を確認するため、本人の保存庫の隔離コピーと、検索前に固定した自然な記憶ベース検索文を任意に集める。記事・メモの本文、質問、正解ラベルをGit管理・外部送信しない。この個別結果を一般性能の主評価に混ぜない。
3. 質問文はタイトル・本文・検索結果を見る前に固定し、本人が候補から正解記事を確認する。複数人の実保存庫データが別途利用可能な場合は追加検証に使い、利用者と正解記事グループを考慮して開発／最終を分離する。
4. 最終分割を一度だけ使う前に、方式、候補深度、モデル、設定、クエリ解析、評価コード、各コーパス指紋を固定する。主指標はクエリ単位Hit@10。成功数／総数、コーパス別結果、95%信頼区間、API失敗・タイムアウト、候補欠落・順位付け失敗を報告する。
5. 同じデータを見て調整した後の再評価は開発データとして扱う。外部評価の対象が保存記事と大きく異なり、未使用の適合データもない場合は95%の一般品質判定を `NOT_EVALUABLE` とする。本人一人の自然検索結果は個別の転移確認にとどめる。

現時点では、外部ベンチマーク上の独立した最終95%達成は確認されていない。JaCWIR探索結果の91.2%は閾値未達で、質問もAI生成のため人間検索の最終評価に不適合。JaGovFaqs、MIRACL、日本語JQaRAは全評価分割を既に使用済みである。JAQKETの人手作成devは日本語記事単位の正解を持つ公開補助候補だが、クイズQAであり、先行JQaRA評価とのqid・正解重複監査で重複グループを除外してから探索・転移用に使う。JAQKET dev1の固定100記事グループではFTS5 81/102（79.41%）、全件E5単独74/102（72.55%）、全件E5＋FTS5 RRF 86/102（84.31%、対象記事グループbootstrap 95%区間76.47–91.18%）。dev2では同設定のFTS5 80/102（78.43%）、全件E5単独73/102（71.57%）、RRF 85/102（83.33%、76.00–90.29%）だった。両splitとも公開devであり、最終holdoutにはできない。RRFは全件埋め込みに約117分を要し、114k件でp95約2.2–2.6秒を要した。JFWIRは多様な日本語Web文書を含むが検索文はAI生成のため開発・性能用。JNQは検索ログ由来で有力だが、公式掲載ページに配布データ本体を確認できていない。NTCIR 2026 ToTは日本語の記憶検索に近いものの、公開devの質問はLLM生成で開発用に限る。Webis-KIQC-13は人手由来の自然なknown-item質問とWebページ正解を持ち、現時点で最も記事検索に近い外部候補だが、ClueWeb09の利用条件・文書取得を未確認である。TREC ToTとReddit-TOMTも課題形式は近いが、対象領域・言語が保存記事と異なる。Reddit-TOMT Books現行APIの開発測定は409/1,842問（22.20%）で、同データを過去の方式探索にも使っているため独立holdoutとして扱わない。したがって外部開発測定は継続中だが、95%達成は未達成・判定保留である。本人の質問収集は保存庫上の個別転移確認に利用できるが、一般性能の主評価にはしない。

NTCIR devの隔離索引作成は `scripts/bench/build_ntcir_tot_ja_index.ts`、全500問のFTS5候補再現・E5再順位の探索評価は `scripts/bench/benchmark_ntcir_tot_ja_dev.ts`。どちらも隔離SQLiteのみを使用し、本番DBを書き換えない。索引の公式MD5・文書数・SQLite整合性は確認済みだが、1問のFTS取得に20.3秒かかったため全500問評価は完了していない。閾値を測る目標対象は1万〜数万件であり、この1.39M文書索引の速度は規定合否には使わない。 |
