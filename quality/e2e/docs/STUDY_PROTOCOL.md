# 事前登録：実利用における再発見率評価

## 母集団と指標

主張対象を収集開始前に固定する。例：「2026年11月に日本語でmy-searchを使用した、事前同意者の初回再発見セッション」。全世界の利用者への外挿は認めない。自然なセッションとは、実際に探す必要が生じた際に、検索結果や正解タイトルを見ず、以前保存した記事を思い出すために入力した検索。評価者が試験のために書いた架空の質問は含めない。対象の記事がセッション開始以前に保存されていたことを後日人間が検証する。保存されていなかった事例を除外するか失敗として数えるかは事前登録し、後から都合よく変更しない（既定は成功と扱わない）。

**第1指標：First-query Hit@10** 実際の初回検索時点に表示されたTop10に、人間が確認した探し物のカードIDが含まれる。検索APIの異常、正解不明、結果なしは失敗。

**第2指標：End-to-end refind success** 初回検索開始から180秒以内、3クエリ以内に利用者が意図した保存済みカードを実際に開いた。検索結果に表示されただけでは成功ではない。タイムアウト・離脱・失敗・未判定は分母に入れて失敗と数える。両方の指標で95%超を要求する。2つの指標を同時に主張する交差和集合型（intersection-union）検定として、各帰無仮説を同じ片側αで棄却する。個別に好きな方だけ成功として宣伝しない。

## 人間が不可欠な部分

1. 同意を取得して、データをローカル保存。暗黙収集は不可。検索語にはPII・秘密が入り得るため厳重管理、明示削除・撤回の権利、保持期間を設計。
2. 検索前に初回クエリ確定。検索時点のTop10・時刻・エラーを記録し、後から同じクエリを再実行した結果とすり替えない。開いたカードID、時間、クエリ数も記録する。
3. 正解カードが本当に検索前から保存されていたか、人間が検索後にIDと内容を検証。メモや本文からの自動生成正解は使わない。
4. 事前に定めた連続適格セッションを漏れなく登録。未成功セッションを捨てない。検定結果を眺めて採集を停止・延長しない。
5. 複数ユーザー一般化の例では、**参加者ごとに初回の自然な1セッションのみ**を評価単位にしてn=500とする。参加者が1人の500セッションを独立な500人と扱わない。
6. ビルド固定（コード指紋、検索対象スナップショットまたは時点の記録、フラグ、既存カード数、言語、対象人口、収集期間）を事前に記録。期間中に改善したらコホートを分割して再登録。

## 統計

帰無仮説は各指標でp <=0.95。対立仮説p>0.95。有意水準の総枠5%を認定試行jに `alpha_j=0.05/(j(j+1))` で配分する。初回片側α=0.025。n=500なら成功485件以上がそれぞれ必要（厳密二項）。厳密信頼下限 >0.95を要求する。固定n・結果の事後改変禁止。連続セッションでも季節・参加者間の選択バイアスはあり得る。これは代表性を数学的に証明するものではない。

500は絶対条件ではない。`tools/sample_plan.py` でnごとのパワーを事前計算し、計画書作成時に数を固定する。例、真の成功率98%のとき、単一指標の500件テストの検出力は約95.3%。両指標が同時に合格する確率は、相関やそれぞれの真の成功率に依存する。複数人採集が十分にできない状況では統計的認定は**NOT_EVALUABLE**とする。

## 自動収集のUI実装要求

CLI `tools/live_study.py` とmy-searchの実UIに記録・手動判定機能を実装した。UIの記録は事前登録済みの固定ビルドでのみ有効となり、成功率・途中集計は表示しない。

- デフォルトOFFの明示同意、ローカルのみの保存。無断で生クエリを送信しない。
- セッション開始で対象カードをUIが先読み・提示しない。初回検索語確定→検索API応答→Top10・ビルドID・発行時刻・カード集合バージョンを同時点で保存。
- リクエスト失敗でも記録。セッション中の再検索回数、実際に開いたカードID、経過時間、打ち切りを記録。単なるTop10表示を「開いた」に転用しない。
- 人間が**検索後に**対象保存カードを指定する確認UI、または不明・失敗を記録する機能。対象が検索前に存在したことを照合する手段を設ける。
- 試験途中は統計結果・成功率をCodexの改善ループに表示しない。集計前の可視性を制限。
- コホート封印、改変検査、事前固定件数、1参加者1セッション選抜、複数回挑戦時のα配分を実装。
- データ撤回と削除の機能、アクセス権、追跡期間、ローカル暗号化の可否を設計する。撤回が出たら、元々予定したnの採集基準への影響を検討し、都合のよい補充をしない。

## my-search UIの事前登録と利用

1. 検索コードを凍結して `python quality/e2e/tools/fingerprint.py --repo . --json` を実行する。
2. `fingerprint` の値で `python quality/e2e/tools/live_study.py init --build-id <指紋> --scope multi-user --n 500 --population "事前登録した同意済み対象集団" --retention-days 30` を実行する。対象人口・n・期間・保持期限は募集前に確定する。保持期限は1〜3650日で指定する。
3. 同じ作業ツリーからmy-searchを再起動する。検索画面の「任意の検索品質調査に参加する」は既定OFF。参加者が自らONにし、自然に探す必要が生じた初回クエリから記録する。
4. 検索後に人が探していた保存カードを選ぶか、対象不明を指定する。カード結果の「メモを読む」を実際に押した操作だけを開封成功候補として記録する。3検索または180秒で未確定なら失敗として閉じる。
5. 検索語・カード集合ID・結果・人手判定は `quality/e2e/study/` に平文JSONLで保存される。ディレクトリはGit除外対象。APIの状態確認・記録要求、またはCLI操作時に保持期限を検査し、期限後はプロトコルと生記録を自動削除して、個人データを含まない期限切れ状態だけを残す。ローカル暗号化は未実装のため、OSアカウントとディスク暗号化で保護する。自動削除を動かすにはmy-search APIまたはCLIを少なくとも一度実行する必要がある。
6. 「参加を撤回して記録を削除」は全コホートの検索語・結果・判定ファイルを消し、試行番号の消費記録だけ残す。途中コホートは認定不能になる。撤回後の新規収集には新しい事前登録が必要。

UI収集はlocalhost API要求だけを受け付ける。ビルド指紋不一致、事前登録なし、封印済み、multi-user参加者IDの重複は拒否し、通常検索は継続する。参加者の実在性・同意・独立性はソフトウェアだけでは証明できない。

`STATISTICALLY_SUPPORTED_CONDITIONAL` は、参加者の自然な検索と人手判定が本当で、採取法・独立性・代表性が守られていると外部監査で確認できる場合にのみ、限定された母集団について使う。「数学的に証明」「全利用者95%保証」と言ってはならない。
