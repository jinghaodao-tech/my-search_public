# 設計判断

My Search App はローカルファーストの知識管理アプリです。このドキュメントでは、採用した技術だけでなく、採用しなかった技術とその理由もまとめます。

## なぜローカルファーストか

個人メモには、学習ログ、作業メモ、未整理のリンク、下書きなどが含まれます。データを標準でローカルに置くことで、プライバシーリスクを下げ、アカウント作成なしで使え、ネットワークがなくても動作します。

## なぜSQLiteか

SQLiteはローカルアプリに向いています。別サーバーが不要で、バックアップしやすく、期待するデータ規模では十分高速です。JSON保存よりも、インデックス、制約、migration、transactionを扱いやすくなります。

## なぜPostgreSQLではないか

PostgreSQLはマルチユーザーのホスト型サービスには強い選択肢です。一方、このアプリは単一ユーザーのローカル利用が中心なので、DBサーバー運用を増やさずにリレーショナルな設計を扱えるSQLiteを選びました。

## なぜElasticsearchではないか

Elasticsearchは大規模検索には強力ですが、別サービス、メモリ消費、インデックス運用、デプロイ複雑性が増えます。このアプリでは、ローカルで説明しやすいBM25を優先しました。

## なぜBM25か

BM25は透明性の高い語彙ベースのランキングです。AIだけに依存する検索よりデバッグしやすく、オフラインでも動き、キーワード中心の知識管理と相性が良いです。

## なぜベクトル検索を中心にしないか

ベクトル検索は意味的な近さを扱うには有効ですが、embedding model、モデル更新、保存容量、ランキング説明性の問題が出ます。まずBM25を安定した基準として実装し、将来の比較対象としてベクトル検索を扱う方針です。

## なぜAI要約を中心機能にしないか

AI要約は便利な補助機能ですが、外部APIキー、利用制限、ネットワークに依存します。検索、CRUD、import/export、SQLite永続化はAPIキーなしでも動く必要があるため、AIは中心ではなく補助機能として扱います。

## なぜJSONからSQLiteへ移行したか

最初のJSON保存は単純でしたが、件数が増えると全体読み書き、リレーション管理、migration、検索用インデックスが扱いづらくなります。SQLiteへ移すことで、ローカルファーストを保ったまま、データ管理の一貫性を上げました。

## なぜtags / linksを中間テーブルにしたか

タグとZettelkastenリンクは、最初はJSON配列として扱っていました。現在は `card_tags` と `card_links` に正規化し、タグ検索、バックリンク、削除時の整合性を扱いやすくしています。APIは互換性のため `tags` / `links` 配列を返し続けます。

## 将来マルチユーザー化するなら

認証、認可、ユーザーごとの所有権、同期、競合解決、監査ログ、tenant-aware schema が必要になります。その場合はSQLiteではなくPostgreSQLを検討し、repository層を境界に移行します。

## データが100万件規模になったら

想定されるボトルネックはトークン解析、全文書のランキング、リレーションの解決、大量の検索結果のソート、単純なテキストフィルタです。改善案としてはSQL側でのフィルタリング、タグのJOIN、FTS5の活用、top-kランキング、増分索引、トークンのバックグラウンド再計算、別の検索インデックスの導入などが考えられます。これらは早すぎる最適化ではなく、ベンチマークに基づいて判断すべきです。

これらのボトルネック(重複排除、top-Kランキング、転置インデックス、部分一致フィルタ)について、実測に基づく個別の番号付き決定は`docs/adr/`を参照してください。
