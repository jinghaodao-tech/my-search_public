# ADR-023: APIステータスコード・エラー形式・冪等性

## 状態

Accepted

## 背景

カード、候補、収集、AI、記事インポートの各ルートで、入力不正、存在しないリソース、状態競合、非同期処理、予期しない例外をクライアントが区別できる必要がある。`200` のレスポンスに失敗を埋め込んだり、すべてを `400` に変換したりすると、クライアントは再試行や障害判定を正しく行えない。

## 決定

1. 成功と失敗をHTTPステータスで表現する。入力不正は `400`、認証失敗は `401`、権限不足は `403`、存在しないリソースは `404`、状態競合は `409`、レート超過は `429`、サーバーまたは上流障害は適切な `5xx` を使う。
2. APIエラーは `{ error, code, requestId, details? }` の共通JSON形式で返す。`code` は機械可読な安定値、`error` は表示用の短いメッセージ、`requestId` はログ照合用とする。
3. Zodによる入力検証に失敗した場合は `validation_failed` と検証詳細を返す。スタックトレースや内部情報はHTTPレスポンスに含めない。
4. サーバー側ではリクエストID、HTTPメソッド、パス、ステータス、処理時間を構造化ログへ記録する。
5. 同じ操作を安全に再送できる処理は、一意制約、トランザクション、または既存の状態確認で重複結果を抑止する。汎用の `Idempotency-Key` 保存・再生機構は、必要なエンドポイントと保存期間を定義した後に追加する。
6. 状態競合は成功に見せかけず、専用の `409` と安定したエラーコードで返す。非同期処理は `202` とジョブ識別子を使い、状態取得APIを別に持つ場合に限り採用する。

## 代替案

- すべての失敗を `200` で返す: HTTPクライアント、監視、再試行処理が失敗を認識できないため採用しない。
- すべてのクライアントエラーを `400` にする: 認証、未存在、競合、レート超過の意味を失うため採用しない。
- すべてのPOSTに直ちに汎用冪等キーを導入する: 保存先、TTL、ペイロード不一致時の扱いを決めずに導入すると、誤った再生や無期限のデータ保持を招くため保留する。
- リポジトリごとに異なるエラー形式を使う: 連携クライアントの分岐を増やすため採用しない。ただしPCSとMeTheoryのドメイン固有コードは各リポジトリのADRで定義する。

## 根拠

- 共通エラー生成とリクエストIDは `services/http_service.ts` に実装されている。
- 入力検証は `schemas/` と各ルートで実施している。
- 競合や重複保存の一部は一意制約・トランザクションで保護している。
- ADR-014はクライアント側の非2xx処理と共通エラー契約を扱い、本ADRはサーバー側のステータス分類と冪等性方針を補完する。

## 結果

クライアントはエラー種別、再試行可否、ログ照合先を機械的に判断できる。現時点では汎用の冪等キー機構と全ルートの完全な競合統一は未実装であり、既存の一意制約・トランザクション・状態確認がある範囲を実装済みとする。

## 見直し条件

外部クライアントからの再送、非同期ジョブ、マルチユーザー運用、分散配置が必要になった場合は、エンドポイントごとに冪等キーの対象、TTL、キーと本文の不一致、レスポンス再生を定義して本ADRを更新する。
