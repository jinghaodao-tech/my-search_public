# ADR-025: 評価指標は自前実装のままとし、参照定義と理論上限で縛る

## 背景

検索品質の指標 — Precision@k、R-Precision、MRR、Recall@5、nDCG@5 — は
`scripts/evaluate_search_quality.ts` に手書きで実装されている。これらには確立した
実装が存在する（`trec_eval`、`ir_measures`、`ranx`）。いずれも Python のツールであり、
本プロジェクトは TypeScript で、評価は `npm run evaluate:search` の一部として実行される。

自前実装は既に欠陥を1つ生んでいる。`precisionAt` は `k` ではなく
`Math.min(k, results.length || k)` で割っている。

```ts
function precisionAt(results: string[], expected: string[], k: number): number {
  const set = new Set(expected);
  return results.slice(0, k).filter(id => set.has(id)).length
       / Math.min(k, results.length || k);
}
```

分母が可変だと、返却件数が `k` 未満のケースが標準定義より高いスコアになる。
実測の Precision@3 が**理論上限を超えた**が、標準定義ではそれは起こり得ない。
発見できたのは、後から理論上限の検査を追加したためである。

Precision@3 はその後 R-Precision に置き換えられたが、`precisionAt` はファイルに残り、
Precision@1 で今も使われている。`k=1` なら分母は必ず1なので現時点の実害はない。
**しかし関数としては誤ったままで、`k>1` で呼べば同じ誤りが再発する。**

## 決定

指標は自前実装のままとする。そのうえで制約を2つ加える。

1. **`precisionAt` の分母を `k` に直す。** 標準定義は
   `(上位k件中の正解数) / k` である。`k` 件未満しか返さなかったクエリは減点される。
   これは正しい挙動で、**何も返さないことは精度ではない。**
2. **すべての指標に参照定義と理論上限を持たせる。** `search_quality_config.ts` の
   各指標に、標準定義を示す1行コメントを付け、`theoreticalUpperBounds` に必ず含める。
   既存の `assertMetricsWithinUpperBounds` は実測が上限を超えると実行を失敗させる。
   これが定義のズレを検出する仕組みになる。

この2つを満たさない指標は追加しない。

## 代替案

- **`ir_measures` や `ranx` を採用する。** 却下。Python であり、評価は索引構築・
  ランキング実行・成果物出力までを含む Node の検証パイプラインの一部である。
  その途中に Python 境界を挟むコストは、指標そのもののコスト（定義を直せば各10行程度）
  を上回る。
- **TREC 形式の run ファイルを出力して `trec_eval` を呼ぶ。** 同じ理由に加え、
  外部バイナリのインストールに評価が依存することになるため却下。
- **参照定義を持たないまま自前実装を続ける。** 却下。これが Precision@3 の欠陥を
  生んだ現状である。指標は数ヶ月にわたって誤っていたが、**何とも比較していなかったため
  気づけなかった。**
- **R-Precision に置き換えたので `precisionAt` を削除する。** 却下。Precision@1 は
  実データスコープの主要ゲートであり、読み手にとって最も分かりやすい指標でもある。
  削除ではなく修正すべきである。

## 影響

- 指標の定義が小さく読みやすいまま保たれ、評価が単一言語のパイプラインで完結する。
- 定義のズレは目視ではなく**理論上限の検査**で捕まる。上限を超えた実測値は、
  構造上、実装の欠陥である。
- 分母を直すと、`k>1` かつ返却件数が `k` 未満のケースで Precision@k が下がる。
  旧値を前提にしたゲートは、そのまま引き継がず**再導出する**こと。
- 指標の正しさに対する責任をプロジェクト側が負う。その責任は信頼ではなく、
  上限検査によって果たされる。

## 撤回方法

指標が標準的な IR 指標を超えて広がった場合 — 段階的関連度、順位相関、実行間の
統計的有意差など — 維持されたライブラリを使う理由が、単一言語パイプラインを保つ
理由を上回る。その時点で TREC 形式の run ファイルを出力し、Node パイプラインの外で
評価する。
