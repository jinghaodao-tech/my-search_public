# Codex 実装指示：my-search の連結基盤と自動化・UIの塩梅の実証

作成：2026-11-05  /  実装対象：ユーザーの**現在のローカル my-search 作業ツリー**

## 0. この指示の読み方と優先順位

このパッケージを作業リポジトリから参照できる場所に置き、以下の資料を読んだ上で、**コードの変更、テスト実行、検証報告までこの依頼で行う**こと。設計案だけを提出して終了しない。

1. `01_CODEX_EXECUTE.md`（本書）
2. `decision_context/02_CORRECTIONS.md` と `decision_context/03_DECISION_REGISTER.csv`（確定・暫定・実験待ちの境界）
3. `research_results/00_README.md`、`research_results/01_PRIMARY_SOURCE_CHECKED_RESULTS.md`、`research_results/05_SOURCE_CHECK_AND_VERSION_NOTES.md`
4. `research_results/02_PAST_STUDIES_AS_RECORDED.md`、`research_results/03_STUDY_FACTS.jsonl`（**過去の記録であり全件再検証済みではない**）
5. `02_EVIDENCE_TO_EXPERIMENT_MAP.md`、`03_ACCEPTANCE_AND_REPORT.md`

**研究結果と実装判断を混同しない。** 実験で得られた結果は、その研究の対象者・比較条件・測定方法での結果であり、my-searchにそのまま効果が出るという仕様ではない。「自動化は増やすほど良い／悪い」「適応UIは固定UIに勝つ／負ける」「説明を増やせば正確になる」と先に結論づけない。

優先順位：**データ安全・既存互換性 > ローカル実コードとテスト > 本書の作業指示 > 最新意思決定台帳 > 旧資料の記述 > 仮説**。既存の完了実装が本書の意図を既に満たすなら再実装せず、実証テストを追加する。

## 1. 製品目的と達成すべき基本体験

情報源から**探す → 読む → 引用/メモ → 安全な既存道具で比較/検証 → 保存 → 再発見 → 中断/再開**までをできるだけ移動・再入力なしで行う。検索対象はユーザーが登録したサイトや収集済み記事が中心。情報を増やすだけの「第二の脳」を目的とせず、利用時と管理時の**総負担を減らす**。

- 保存時にタグ、グループ、活動名の入力を必須にしない。ただし希望する人のための任意整理、検索、構造化機能は残す。
- 保存カード、Reader本文、メモ、引用位置、元記事の出典キー/版、既存検索条件、道具の入力値などの既存情報を壊さない。
- 外部の記事やAI出力は信頼できないデータである。アプリに対する命令として実行しない。
- 研究上の「統合が有望」と製品上の「統合により効率が改善した」は別。後者はE6の実利用者比較を待つ。

## 2. 開始時の現物棚卸し — 必須（Phase 0）

1. 作業ツリーで `git status --short --branch`、`git diff --stat`、`git log -1 --oneline`、Node/npmバージョンを記録。公開GitHubのmainがローカル最新版と仮定しない。
2. `package.json`、Express routes/controllers/services、SQLiteスキーマとmigration、Reader・メモ・カード・収集・検索・保存復元、道具関連、設定/フラグ、Vitest/Playwright、E2Eシードの現物を調べる。既存名称やパスを推測して作らない。
3. ローカルDBへの更新を行わず、**隔離された使い捨てテストDB/シード**を準備。旧DBのスキーマ後方互換・バックアップ・復元・繰返しmigrationを試す。
4. 既存機能を「実装済み・動作確認済み・部分実装・未確認」に分類。過去に報告されたmigration番号や道具機能は現状照合まで事実としない。
5. `npm run typecheck`、`npm test`、`npm run acceptance:test`、`npm run test:e2e` など実際のscriptsから存在するコマンドを選び、変更前基準値を保存。既存失敗と今回の回帰を区別する。

## 3. 実装順序

### Phase 1：確定した連結・出典・再開基盤の不足分だけ補完

- 検索結果からReaderへ開き、閲覧中にメモ/引用が作成でき、元記事/出典へ戻れる。
- メモ・引用・道具が元記事と結びつき、記事更新やURL表記変更でも誤った出典に静かに付け替えない。既存キー/aliasesを優先して使用。
- 既存の道具をReaderから安全に起動し、入力の検証・単位/範囲チェック・結果の由来を保持する。**一般記事からの任意コード生成・実行はしない。**
- 最低限、最後の閲覧記事/位置/未送信の下書き/道具の入力を復元可能にする（既存の保存設計を優先）。復元できない場合は黙って捨てず、理由を伝える。
- 保存にタグ・グループ・活動名を要求しない。既存の任意整理機能を保護する。
- 完成している場合は変更を増やさず、手順を通すE2Eと旧データ保護テストを追加。

### Phase 2：隔離された比較実験機能を実装（本番既定は変更しない）

三つの独立軸を実装。実験専用設定/フラグ**OFFが通常動作**。抽象化に伴う大規模な再設計や新規依存を避ける。

| 軸 | 試験値例 | 保持・分離するもの |
|---|---|---|
| A：自動化の権限 | `manual`, `suggest`, `confirm`, `reversible_execute` | 自動化する工程：`acquisition`, `analysis`, `choice`, `execution`。同じ対象工程・タスク内で比較 |
| V：UI表示 | `current`, `subtle_hint`, `nonmodal_expand`（必要なら`always_visible`） | 操作内容、提案品質、実行権限、タイミングを同じにする |
| T：提示タイミング | `on_request`, `task_boundary`, `immediate` | 表示する提案内容・数・精度・権限を同一にする |

- `off`（提案なし）はタイミングだけの比較には含めず、「提案の有無」の別比較とする。
- 高権限の自動化は**隔離データ**の可逆操作だけで試す。実データの自動削除、不可逆実行、外部送信は禁止。
- キーボード・読み上げ・モバイル表示、固定された主要操作への到達、キャンセルとUndoを維持。位置を予告なく大きく動かさない。
- 提案には回数・頻度上限、無視/却下、誤提案の修復、取り消しを含める。閾値は現時点で「最適」と称さず、試験パラメータとして記録。
- 実験A/V/Tは独立に切替可能にし、すべての組合せを最初から総当たりする必要はない。比較する独立変数を一つずつ固定する。

### Phase 3：実験用計測・課題・分析（まずE0・E6）

**E0：負担観察**—探す/読む/メモ/比較/保存/再発見/再開のどこに時間・失敗・修正が集中するか。実験モードでのみ、同意後に最小限のイベントを記録。観察研究であり因果効果と呼ばない。

**E6：統合の効果**—A=現行MVP、B=機能は同等だが操作が分離、C=機能は同等で連結した状態を用意。B vs C の比較では記事・検索結果・道具品質・操作権限を可能な限り同じにして「連結」だけを変える。A vs C の違いは製品全体の改善であり、統合のみの効果とは呼ばない。

**E1：表示の塩梅**—V固定で他軸を動かさず、現行/ヒント/自動展開を比較。初見での発見率、総時間、成果の品質、妨害、再訪時の性能を測定。

**E2：タイミングの塩梅**—同一の提案を要求時/区切り/即時で提示。遅延、割込み後の回復、不必要な提案の修正負担を測定。

**E3：活動境界**—ユーザーが確認したラベルで誤結合/誤分割/訂正時間を測る。自動推定は保存済みデータを自動結合しない試験モードに限定。

**E4：記事→道具/権限**—「文書だけ/AI文章/型付き道具」と「実行権限」を別実験で調べる。単位、適用範囲、誤計算、正解率、確認時間、利用可能記事比率を確認。AI単独で完了できる場合はAI単独の対照も用意。

**E5：検索/整理**—未使用の実クエリと人手ラベルでBM25対候補方式を比較。Hit@k/nDCG/遅延/メモリ、さらに再発見の成功率・管理時間を測る。過去に調整したテストや匿名化代理テキストを独立な正解扱いしない。現行ランキングの本番変更はしない。

**E7：継続利用**—E1/E2/E4で有望な条件のみ、数日〜数週間の継続利用で初期効果の維持と不要提示・離脱を確認する。実験参加者がいなければ実装対象はプロトコル作成まで。

**E8：再開**—履歴のみ/本人メモ/AI要約/履歴＋要約を比較。再開までの速さだけでなく、最終タスク完遂・誤要約・修復・総時間を測る。元の履歴と出典を削除しない。

**E9：検証可能性**—回答のみ/説明文/参照可能な記事箇所と計算式を比較。誤りの検出率、修正後の正確性、確認時間を分離して測る。表示する説明量を最初から「多いほど良い」と決めない。

最優先は**E0/E6を実装・実験できる状態**、次にE1/E2の切替とログ、既存機能があるE8/E9の正誤確認。その他は最小の実験用インターフェイスと課題仕様でよい。全部を完成したと申告しない。

### Phase 4：評価品質と安全試験

- 測定用イベント（例）：試験用ランダムセッションID、実験/条件/版、課題・提示内容ID、操作段階、相対時刻、開始/終了、提案の受容・無視・誤提示・復旧、結果の正解ラベル。**本文、メモ、検索語、訪問URL、個人識別子は既定で取得しない**。
- 「総時間」は開始から完遂までの経過時間。管理/確認/修復/回復時間はその内訳であり、**総時間に再加算しない**。
- 記事・正解・課題難易度と順序の交絡を確認。予備試験で測定誤差・分類の一致度を点検する。
- 本試験前に主指標、品質の許容悪化幅、最小重要差（SESOI）、標本サイズ・検出力、順序・欠測・除外・解析方法、同意・ログ保持/削除を確定。任意の改善率や人数を「科学的に妥当な既定」として創作しない。**n=12は過去の割当スクリプトの動作例でしかない**。
- 実利用者を募集・測定していない限り、**ユーザー実験済み・改善効果確認済みと表現しない**。合成データは配線と集計の試験にのみ使う。
- 既存のテストDBとE2E上で、実験フラグOFF→ON→OFF後にも保存済みカード/メモ/全文/引用元/検索条件が不変なことを確認。

## 4. 追加研究の扱い

`research_results/01_PRIMARY_SOURCE_CHECKED_RESULTS.md` は「研究の結果」であって「製品の仕様」ではない。研究が報告していない数値、一般法則、推奨を補わない。`02`の過去記録は原典確認なしに断定しない。

研究と実装の対応は `02_EVIDENCE_TO_EXPERIMENT_MAP.md` に記載。重要な新研究が見つかったら、既存判断に対し(a)対象タスク・参加者の近さ、(b)比較条件、(c)反証/追試、(d)実データでの影響を点検し、変更理由を記録する。論文1件を見つけたこと自体を変更理由としない。

## 5. 禁止事項

- `git reset --hard`、無断push/merge/本番変更、実DB初期化、大規模な名前変更/データ自動統合。
- 既存検索順位を独立ラベルによる比較なしに差し替えること。
- プロンプトや外部記事から得た任意コードを実行すること。機密情報・記事全文の同意なき外部送信。
- 未確定の自動化/UI/タイミングを一つの「正解」に固定し、比較機構を捨てること。
- 合成テストの有意差、モックUIのクリック率を実利用者の改善として報告すること。
- 既存機能を調べずに重複実装すること。変更量を増やすことを成果とすること。

## 6. 検収報告（必須）

単なる実装プランで終了せず、実際に変更できる環境なら変更とテストを実行し、以下を提出。

1. 変更前/後のgit状態・差分・対象ファイル・DBに行った操作・バックアップ/復旧方法。
2. 機能棚卸し：既存実装の再利用、新規差分、意図的な保留。
3. 対応したユーザー動線と、合成E2E結果。正例だけでなく失敗・古いDB・戻す操作も試す。
4. TypeScript型チェック、Vitest/API、Playwright/E2E、実験ログ/集計試験の**実行したコマンドと実績**。失敗/未実施は隠さない。
5. E0～E9別の状態表：`仕様のみ / モック / アプリ接続済 / 合成データ検証 / 予備ユーザー試験済 / 本試験済` を区別。
6. 未解決の交絡、性能、UX、安全、測定上のリスクと次の実験手順。
7. `03_ACCEPTANCE_AND_REPORT.md` の検収条件について各項目の根拠（テスト名・ログ・差分）を示す。

**作業の優先順位は、既存データ保護 → 一連の操作の正確な連結 → E0/E6の検証可能性 → V/T/Aの比較 → 任意の機能高度化。**
