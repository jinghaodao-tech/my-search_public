# 現在のmy-searchと実装に関する前提

## 目的（ユーザーが選んだ方向性）
指定した情報源から「探す→読む→引用/メモ→比較/安全な既存ツール→保存→再発見/中断・再開」を連結する。第二の脳化を目標とせず、管理のための活動名・必須タグ・常設整理画面・操作を減らす。利用者が望むときの任意整理は残す。

## 現時点で把握している実装（要現物確認）
- TypeScript/Express、SQLite、BM25/FTS5、RSS/Atom/arXiv/GitHub収集、Reader、カード/メモ、Playwright/Vitestを利用する公開リポジトリ `jinghaodao-tech/my-search_public` を過去に確認した。
- 公開`main`がローカル作業ツリーの最新版とは限らない。ローカルの未コミット変更、branch、migration履歴、DBを必ず確認する。
- 過去の報告には固定宣言形式Readerツール、道具状態保存・復元、migration 026、トークン検索実験などがあるが、この資料作成時点のローカル再実行はしていない。
- 既存UI/API/スキーマのパスや名称を推測して新実装を作らない。実装の重複を避ける。

## 本番に固定してよいもの（『研究によって効果が証明済み』の意味ではない）
1. 保存カード、メモ、元記事本文、旧出典IDを破壊・黙って付け替えない。記事更新時の不整合を検出し復旧可能にする。
2. 検索→Reader→メモ/道具→保存→復元へ到達できる基礎フローを作る。
3. タグ/グループ/活動名は保存の必須入力にしない。任意編集機能は守る。
4. 外部記事をアプリへの命令として実行しない。未知の生成コードの実行をしない。無許可外部送信をしない。
5. 旧UI、検索、Readerを、実験フラグOFFで現行どおり動く状態に保つ。

## 現時点で固定しないもの
- 高/低自動化、提示箇所とタイミング、自動区切り、提案頻度、AI説明量、個別のランカー（BM25からの置換）、生成道具の自動公開、長期保存量。
- 製品の優位性（統合することで本当に時間と管理負担が減るか）。この部分はユーザー試験が必要。

## 作業ツリーで最初に確認すること
- `git status --short --branch`、`git diff --stat`、`package.json`、Reader/検索/メモの現物、検索条件保持、migration、DBパス（read-only）。
- 隔離テストDBを作り、旧DBのバックアップは書き換えずにmigration/復元をテスト。
- すでに機能を満たす場合は**変更せずE2Eを追加**してよい。

## 禁止
`git reset --hard` / 無断push・本番merge / 実DB初期化 / 手動カード統合 / 大規模リネーム / 同意のない閲覧ログ全収集 / 本番の無検証ランキング変更 / 外部AI強制 / 生成コードの任意実行。
