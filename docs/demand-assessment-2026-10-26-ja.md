# my-search 需要調査と製品仮説

調査日: 2026-10-26。公開情報による机上調査と現行リポジトリの確認。ユーザーインタビュー、利用ログ分析、購入実験は未実施。需要規模・支払意思・競合に対する優位性は未検証。以下の優先順位・数値は、既存目標として明記したものを除き提案であり、人間の承認済み要件ではない。

## 判断

記事の保存、再発見、情報収集には既存の製品カテゴリーと有料プランがある。したがって課題と商用の提供先は存在する。ただし「my-searchが選ばれる」「十分な人数が購入する」は別の仮説で、まだ証明できない。

最初に検証する価値が高いのは、**日本語の記事・メモを多く保存する人が、タイトルを忘れても、内容の記憶から必要な資料に戻れること**。保存・分類・AI要約をすべて広げるより、この作業が既存手段より速く完了するかを測る。

競合も全文検索や意味検索を持つため、「日本語」「ローカル」「AI検索」の名称だけでは差別化は成立しない。日本語の曖昧な検索での成功率、導入の容易さ、取り込みの確実性、データを手元に残せることの組み合わせで比較する。

## 誰の、どの需要を満たすか

| 候補層 | 困る場面と求める成果 | 優先仮説 | 競合・代替 |
|---|---|---|---|
| 日本語の技術記事を多く保存する開発者・技術ライター | 実装中に「あの解説」を探し直し、作業を再開したい | 最初の対象。既存の検索・記事保存と近い | ブラウザ履歴、Google、Raindrop、Obsidian |
| 調査・企画・執筆を繰り返す個人 | 記事と自分のメモを、出典付きで再利用したい | 次点。引用箇所と保存理由の需要を確認 | Readwise、Notion、文書・ノート検索 |
| 特定テーマを継続監視する人 | 新着のうち読むべきものだけ選びたい | 別系統として検証。収集範囲と鮮度が重要 | Inoreader、RSS、ニュースレター |
| 自分のデータを外部に預けたくない人 | オフライン利用、移行、終了時の持ち出しを確保したい | 横断的な選択条件。これ単独の主用途とは限らない | ローカルファイル、Obsidian、Karakeep |
| 一般的な「あとで読む」利用者 | スマホですぐ保存し、すぐ読みたい | 初期は優先を下げる。PCローカルだけでは適合しにくい | ブラウザ保存、各種読書アプリ |

「保存件数が多い」だけでは対象条件にならない。直近1か月に探し直せず困り、検索に時間を使い、既存手段への不満がある人を優先する。目安として数百〜数千件を募集条件の候補にするが、需要の境界値と断定しない。

## 必要な品質

次の値は競合から導いた市場標準ではない。既存の技術目標と、需要検証のための提案を区別する。

| 項目 | 目標・合格候補 | 扱い |
|---|---|---|
| 検索の一般能力 | 未使用の人手由来known-item評価でHit@10 95%以上 | [既存目標](search-goals-ja.md)。対象領域ごとに評価し、全ユーザーの成功率と同一視しない |
| 利用者の作業成功 | 探し直す課題を初回検索から30秒以内に完了。試用段階は80%以上を仮目標 | 提案。結果表示だけでなく正解の確認まで計測。失敗数・人数・区間も報告 |
| 応答速度 | 現PC・1万件・索引準備後で検索API p95が3回とも500ms以下 | 既存目標。初回起動・索引作成・UI描画を別途計測 |
| 保存と索引 | 保存成功表示の後、本文とメモが再起動後も残り、再検索できる | 必須の信頼性。障害・バックアップ復元・移行で検証。試験で損失0件でも無事故保証とはしない |
| 導入 | 対象利用者が手助けなしで5分以内に最初の記事を保存・検索できる | 提案。通常利用者にnpmやAPIキーを必須にしない構成を検討 |
| 取得品質 | 支援対象サイトで本文抽出成功率95%以上、失敗を全件明示 | 提案。対象URL集合・成功判定・除外を事前固定。ログイン・課金壁の突破を要件にしない |
| 誤解の防止 | 収集0件、対象0件、該当0件、索引未準備、取得失敗を区別 | 高精度スコアと独立した品質条件 |
| データ制御 | 外部送信される操作と内容が分かり、通常の保存・検索を有料AIなしで使える | ローカルを選択理由にする層向け。外部AI要約やWeb探索の送信も明示 |
| 新規記事発見 | まず利用者の関連性評価と、既存手段に対する有用記事到達時間で比較 | 別評価。nDCG@10等の品質閾値を再発見の95%から流用しない |

30秒・80%・5分・抽出95%は初期実験の仮閾値であり、要求水準の確定には観察が必要。Hit@10だけ良くても、10件を読み比べる負担が大きければ製品価値は低い。成功率・検索し直し回数・正解確認までの時間を併せて見る。

## 現在の品質について言える範囲

[2026-10-25の暫定方式記録](saved-card-search-default-decision-2026-10-25-ja.md)には、FTS5形態素の既定経路で1万件のp95約336〜342ms、APIエラー0件という測定がある。今回の調査では再測定していない。現行コードにもFTS5経路が存在することを確認した。

同記録の本人確認済み6問の成功は小標本・開発用であり、一般性能95%の達成根拠にならない。2026-10-26の[検索目標](search-goals-ja.md)と[評価範囲](../quality/e2e/docs/EXTERNAL-AND-PERSONAL-EVALUATION-SCOPES-ja.md)に従い、一般能力の主評価は外部の人手由来データで行う。本人に一般性能評価用の質問作成を必須にしない。需要調査への参加と検索品質評価のデータ作成は別の活動である。

READMEには保存カード検索をLIKEとする説明も残っており、最新の方式記録・コードと差がある。市場調査ではREADMEだけを現在の実装状態として扱わない。今回は既存文書・実装を変更しない。

## 需要を確認する次の実験

これは実施計画の提案であり、募集・連絡・個人情報収集・課金は行っていない。

1. **課題インタビュー8〜12人**。開発者・ライターを中心に、既存ツールに満足する人も含める。「欲しい機能」より、直近に探せなかった記事、頻度、所要時間、代替策、現在の支払い、端末を聞く。同じ具体的な課題が複数人で繰り返されるか見る。便宜抽出なので人口比率を推定しない。
2. **5〜8人の比較試用**。普段の手段とmy-searchで、同程度の課題に到達できるか比較。正解を先に見せない。順序・課題難度・学習効果に配慮する。本人データの提供を強制せず、許可されたコピー・ローカル実行で扱う。
3. **2週間の継続観察**。検索機会が何回あったかを分母にし、実際に使ったか、見つかったか、元の手段に戻った理由を記録。毎日使わないことだけで失敗扱いしない。仮の継続判断は、8人中4人以上が別々の週に自発的に検索し、複数人で時間短縮が確認できること。市場適合の証明には不足する。
4. **乗り換えと支払意思の確認**。既存ツールからの移行作業、継続利用の選択を確認する。将来有料化する場合は、例として買い切り3,000〜6,000円または月300〜600円を別々の仮説として提示できる。ただし価格調査未実施で、推奨価格ではない。アンケートの購入意向と、条件を明示した実購入・予約の証拠を分ける。

継続する理由が「整理しなくても再発見できる」なら検索・取り込みを強化する。「スマホから保存できない」で離脱するなら端末間導線を優先する。「新着の選別」に集中するなら監視用途を別案として検証する。課題が希少、既存手段より遅い、導入後も使われない場合は、機能追加を止めて対象層や用途を見直す。
