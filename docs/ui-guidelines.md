# UI 操作統合ガイドライン

## 基本原則

- 利用者の目的ごとに主要な操作経路を一つ設ける。カード編集は `openEditModal` から共有Editorを開き、作成・更新とも同じ `saveReaderCard` を使う。
- PCとスマートフォンでDOM、入力状態、保存処理を共有する。画面幅による変更はCSSのレイアウトだけにする。
- カード種別ごとの差は共有Editor内の条件表示と保存アダプターで扱う。Reader形式の記事・PDFは `/api/reader/*`、通常カードは `/api/cards/*` に保存する。
- タグとカード色も共有Editorから保存する。タグを個別の隠れた保存経路へ分けない。
- Readerの保存済み原文・段落・PDFページ標識は閲覧専用として扱う。利用者が編集するタイトル、URL、出典メタデータ、タグ、メモと明確に分ける。
- 引用元の本文・位置情報を更新するときは、出典の同一性を確かめる。原文を再取得する操作と保存内容を編集する操作を混同しない。
- 削除、アーカイブ、エクスポート、カード間リンクのようにデータへの影響が異なる操作は編集へ押し込まない。編集画面内に削除確認を置く場合も、編集保存とは別の明示操作にする。
- AI支援、候補作成、要約は自動実行や通常保存と混同しない。入力元、処理、結果、保存の違いを表示する。
- 同じ処理を表すボタンには同じ動詞・名称を使う。異なる副作用を持つ操作は、対象や結果が分かる名称に分ける。
- 主操作は画面内で見つけやすくし、補助・一括・破壊的操作は主操作と区別する。便利な一覧ショートカットは、詳細画面の入口と同じ処理へ接続して残す。
- すべての主要画面とモーダルについて、利用者の目的、表示名、呼び出し先、統合判断を `docs/ui-operation-audit.md` に対応付ける。

## 標準用語と配置

| 表示名 | 目的・使い分け |
|---|---|
| 編集 | 保存済みカードのタイトル・URL・タグ・メモ・出典メタデータを編集する。詳細の主要入口と一覧の鉛筆ショートカットは同じEditorを開く。 |
| 読んでメモ | URLやPDFをReaderへ新しく読み込む。保存済みカードの編集には使わない。 |
| 保存 | Editorの変更を保存する主操作。カード種別によるAPI差は内部アダプターに閉じ込める。 |
| 情報源を管理 | 情報源設定の同じ管理画面を開く。管理メニュー・検索画面など入口ごとに名称を変えない。 |
| データ取り込み | CSV/JSONなどの保存データを取り込む同じ画面を開く。形式の違いは画面内で選ぶ。 |
| Markdown出力 | 1件または選択カードのMarkdownを書き出す。対象数は実行前に分かるようにする。 |
| 削除 | 対象データを削除する破壊的操作。アーカイブ・非表示とは別名にし、対象を確認してから実行する。 |

- 同じ動作のアイコンボタンは表示テキストとアクセシブル名をそろえる。短い見た目を使う場合も `aria-label` で同じ操作名を提供する。
- 1画面内では保存・作成などの主操作を一貫した位置に置き、閉じる・キャンセルを二次操作、削除・参加撤回などを確認付きの破壊的操作として視覚的に分ける。
- 「読んでメモ」と「編集」、「アーカイブ」と「削除」、「引用をコピー」と「引用を別メモへ追加」のように対象や副作用が異なる操作は、同じ名前にまとめない。

## 新しい操作を加える前の確認

1. 操作の目的、対象データ、不可逆性を記述する。
2. 同じ目的のボタン、モーダル、画面、API呼び出しを検索する。
3. 既存画面へ条件付きの一項目として統合できるか検討する。
4. 統合できない場合は、対象データまたは副作用が異なる理由を画面か設計文書に残す。
5. PC・スマホで同じ保存・失敗処理を使うことをE2Eで確かめる。
6. 元データ、メモ、引用、出典情報の保存前後を比較する。

## 自動チェック

`npm run check:ui-guidelines` は編集入口の共通化、重複詳細ボタンの不在、主要画面・モーダルの監査表への登録、保存形式とReader原文の保護を静的に検査する。これはDOMと呼び出し先の整合確認であり、画面操作・アクセシビリティ・データ保護のE2E検証の代わりにはならない。画面やモーダルを追加した場合は、先に監査表と `e2e/ui-surface-audit.spec.ts` を更新する。
