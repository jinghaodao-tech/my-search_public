# UI 操作統合ガイドライン

## 基本原則

- 利用者の目的ごとに主要な操作経路を一つ設ける。カード編集は `openEditModal` から共有Editorを開き、作成・更新とも同じ `saveReaderCard` を使う。
- PCとスマートフォンでDOM、入力状態、保存処理を共有する。画面幅による変更はCSSのレイアウトだけにする。
- カード種別ごとの差は共有Editor内の条件表示と保存アダプターで扱う。Reader形式の記事・PDFは `/api/reader/*`、通常カードは `/api/cards/*` に保存する。
- タグとカード色も共有Editorから保存する。タグを個別の隠れた保存経路へ分けない。
- Readerの保存済み原文・段落・PDFページ標識は閲覧専用として扱う。利用者が編集するタイトル、URL、出典メタデータ、タグ、メモと明確に分ける。
- 引用元の本文・位置情報を更新するときは、出典の同一性を確かめる。原文を再取得する操作と保存内容を編集する操作を混同しない。
- 削除、アーカイブ、エクスポート、カード間リンクのようにデータへの影響が異なる操作は編集へ押し込まない。編集画面内に削除確認を置く場合も、編集保存とは別の明示操作にする。
- AI支援、候補作成、要約は自動実行や通常保存と混同しない。入力元、処理、結果、保存の違いを表示する。

## 新しい操作を加える前の確認

1. 操作の目的、対象データ、不可逆性を記述する。
2. 同じ目的のボタン、モーダル、画面、API呼び出しを検索する。
3. 既存画面へ条件付きの一項目として統合できるか検討する。
4. 統合できない場合は、対象データまたは副作用が異なる理由を画面か設計文書に残す。
5. PC・スマホで同じ保存・失敗処理を使うことをE2Eで確かめる。
6. 元データ、メモ、引用、出典情報の保存前後を比較する。

## 自動チェック

`npm run check:ui-guidelines` はカード編集の画面・保存経路が分裂していないことを静的に検査する。これはDOMと呼び出し先の整合確認であり、画面操作・アクセシビリティ・データ保護のE2E検証の代わりにはならない。
