# my-search UI設計ルール

このルールは、検索・閲覧・メモ・保存・整理を一続きに使うローカルアプリの画面を保つためのレビュー基準です。機能を追加するときは、通常時の画面占有、操作起点、失敗時の戻り方、既存導線への影響を確認します。

## 画面の優先順位

- 最上位にはカード一覧、候補レビュー、検索、Readerなど、日常の目的に直結する入口を置く。
- 低頻度の管理操作は二次導線に置く。頻繁な操作を折りたたみの奥へ移さない。
- 操作名は内部機能名より、利用者の作業（探す、読む、メモ、整理）に合わせる。
- 既存機能を隠す場合も、見つけやすく到達可能な経路を残し、到達テストを行う。

## 必要な時だけ現れる補助機能

- 補助機能は通常時に専用タブ、起動確認ボタン、常設パネルを増やさず、記事の対象箇所や既存の入力操作から始める。
- 操作中に必要な入力と結果だけを近くに表示し、閉じる／Escapeで元の作業へ戻れるようにする。
- 非対応、未確定、機能停止、通信・保存エラーでは、通常の閲覧・メモ・保存へ安全に戻す。
- 関連機能は既存画面の文脈へ統合し、単に別メニューへ移すだけで整理済みとしない。

## 状態と回復

- 表示切替や補助パネルの開閉で、入力中の本文、メモ、値、閲覧位置を失わせない。
- 保存値は元の記事・カードを識別できる情報と結び付ける。元データが変わった状態を黙って再利用しない。
- 保存の成功・失敗を画面で分かるようにし、失敗時に既存データを部分更新しない。
- データ形式変更はバックアップ、トランザクション、旧データ読み込みの確認を伴わせる。

## キーボード、タッチ、読み上げ

- クリック可能な要素には同等のキーボード操作、見えるフォーカス、意味のあるラベルを用意する。
- hoverだけで操作可能性を伝えない。タッチ操作で同じ機能に到達できるようにする。
- 動的な結果やエラーは適切な状態通知を付ける。表には行・列見出しを使う。
- 自動テストで操作経路を確認し、スクリーンリーダーの手動確認が未実施なら検証バックログに残す。

## 追加時のレビュー項目

1. 既存のどの操作へ結び付けられるか。
2. 通常時に見えなくてよい要素は何か。
3. 対象外・エラー・機能停止時にどう通常状態へ戻るか。
4. 主要タスクにクリック、画面移動、待ち時間を追加しないか。
5. デスクトップと狭い画面、キーボード、タッチで使えるか。
6. 誤操作を戻せるか。保存状態や出典を確認できるか。
7. E2Eで既存導線の到達性と通常時の非表示状態を確認したか。

画面を小さくすること自体は合格条件ではありません。補助要素を隠すことで発見性や主要作業の速さを下げていないかを、シナリオで確認します。
